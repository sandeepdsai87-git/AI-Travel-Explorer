1. Product vision and status

Help travelers discover destinations and experiences, plan editable and realistic multi-city journeys, assess transport feasibility, estimate trip costs and compare external booking providers without booking or processing payments within the initial product.

Target: India-first; solo travelers, families, groups, pilgrims, budget travelers and other travel styles. Core hypothesis: destination-first planning with public-transport-aware feasibility and protected must-visit stops is a useful differentiator, not yet a proven market gap.

Document authority: Research draft based on Blueprint v0.3 and initial hands-on competitor observations. Requirements and phase assignments are proposals until approved. This file is not an architecture specification or authorization to implement.

Evidence boundary: No live train/bus availability, fares, timetables, temple opening hours, accommodation inventory or booking integrations are connected. Examples below are illustrative, not validated travel advice.

Goals and measurable validation hypotheses

  • Allow a traveler to specify dates, traveler count, preferences, must-visit places and an ordered multi-city route.
  • Generate a reviewable day-by-day plan and flag unsupported or conflicting travel assumptions rather than presenting invented certainty.
  • Let travelers edit plans while preserving explicitly locked stops.
  • Validate whether required Indian transport data, commercial access and unit economics can support this promise before development.

Numerical success thresholds, launch targets and KPIs remain TBD; no metrics are fabricated in this draft.

v0.7 — Dual-entry, dual-duration discovery and context-aware UX

Decision: The platform is destination-independent and supports two equally valid starting paths. Both paths feed one shared trip model and one feasibility-aware planning engine. The traveler is not required to know a full route in advance.

Two starting paths × two duration modes

Starting pathFixed days (time-constrained)Flexible days (destination-constrained)

Destination discovery and journey feasibility rules

  • Discover both within-destination experiences and regional destinations reachable by practical journeys, including overnight train/bus and road connections; do not apply an arbitrary radius as the sole relevance criterion.
  • Rank suggestions by traveler interests, estimated door-to-door travel burden, connection quality, visiting time, available days, budget and pace. Display why a place is suggested and the evidence/uncertainty behind any travel claim.
  • Provide must-visit and optional status at destination and attraction levels. Never silently drop or replace a must-visit; seek explicit user action when constraints conflict.
  • Allow travelers to switch entry path or duration mode, add/remove destinations, change priority, and override route order without losing selections. Re-evaluate dependent transport, itinerary and budget assumptions.
  • Show both minimum practical and comfortable recommended duration estimates, with transparent assumptions and uncertainty; where source coverage is insufficient, state that a reliable estimate cannot yet be confirmed.
  • Fixed-day plans must flag infeasible combinations and propose alternatives such as fewer optional stops, a different visiting order, or extra days. Never fabricate a service or treat overnight travel as guaranteed.
  • Destination search must support arbitrary places, not a fixed set of sample cities. Illustrative examples must be labeled and unknown results handled with a useful manual-entry fallback.

Minimum data contracts and replaceable boundaries

Use stable IDs rather than matching on place names. Proposed typed records:

  • Destination: id, canonical name, type (city/town/region/landmark), parent geography, coordinates when supported, provider reference, provenance.
  • Attraction / experience: id, destination association, category, description, verified opening information if available, estimated visit duration if sourced, provenance.
  • Image asset: associated place ID, authorized source, image URL or approved local asset, attribution text, rights/license metadata, retrieval date, fallback status.
  • Transport option: origin/destination IDs, ordered legs, mode, time window, indicative duration/cost only when grounded, operating-day caveats, verification link, source and unbooked status.
  • Trip and itinerary: origin, primary and selected destinations, ordered stops, travel dates or flexible duration, must-visit flags, activities, provisional transport, conflicts, estimate provenance and change/reconciliation state.
  • Estimate: value/range where grounded, currency/unit, source, calculation assumptions, confidence, freshness and unknown status.

Provider boundaries: DestinationSearchProvider, RegionalDiscoveryProvider, PlacesProvider, ImageProvider, TransportProvider and Estimate/FeasibilityProvider. A clearly labeled FixtureProvider is allowed for frontend demonstrations only. Provider response validation, loading/empty/error states, caching/freshness and attribution are mandatory concerns.

Reactive state and stale-data rules

  1. When origin, primary destination, dates, duration mode or route changes, identify dependent discovery, transport, itinerary and budget data.
  2. Cancel or disregard out-of-order provider responses; never display results from a previous destination as current results.
  3. Retain compatible user selections; flag incompatible selections for review rather than silently deleting protected must-visits.
  4. Recompute estimates only from supported facts and disclosed assumptions; show pending/unknown where providers cannot answer.
  5. Maintain both entry paths (Help Me Discover / I Know My Places) and both duration modes (Fixed Days / Flexible Days) through the same trip state and planning engine.

Imagery quality, rights and fallback policy

Images must be relevant to the actual destination or clearly identified as generic inspiration; never mislabel an unrelated photograph as a specific destination. Preserve required creator/provider attribution and permitted usage conditions. If no authorized, accurate image is available, show a designed place-neutral fallback, not a broken image or falsely captioned photograph. Image-source coverage, costs and commercial permissions must be verified before production use.

5. Planning-first transport and booking-document workflow — v0.2 decision

Approved product behavior: A traveler can build and review a complete multi-day itinerary before purchasing any ticket or reserving a hotel. Booking is never a prerequisite for planning, transport selection, sightseeing, budgeting or itinerary editing.

Core journey: Discover destinations → identify train/bus options → select preferred (unbooked) services → plan and refine the entire trip → verify and book externally → optionally upload confirmations → reconcile booked details with the itinerary.

Explicitly deferred

Required planning workflow and transport states

Discover → Suggest transport → Select provisional/unbooked options → Generate complete itinerary → Refine → Book on provider website → Optionally upload confirmations → Reconcile itinerary.

Transport states: Suggested (source-backed candidate), Selected / Not booked (user planning choice), and Booked / Confirmed by user (details supplied and accepted by traveler). A booking must never be a prerequisite for itinerary generation.

Source and booking-link policy

  • Display route, provider, train/bus number where known, indicative departure/arrival times, operating-day/date caveats, source and last-checked date where available.
  • Link to the official provider's search or booking portal; do not imply that a general portal link deep-links to the exact selected service.
  • Do not automatically ingest restricted sources or claim commercial reuse rights without checking their terms or obtaining permission. Public visibility alone is not a reuse licence.
  • Where reliable options cannot be found, show a clear coverage gap, official verification link and a manual transport-entry option.

Itinerary feasibility requirements

  • Calculate journey duration across dates, overnight arrivals, transfer time and realistic buffers.
  • Preserve user-locked destinations and activities; warn when the requested duration cannot accommodate them.
  • Separate verified schedules from illustrative assumptions; do not invent departures, live availability or exact prices.
  • Recheck conflicts when the traveler changes selected transport, dates, attractions or uploaded booking details.

Document and data requirements

  • Allow optional ticket/hotel-confirmation upload; extract only necessary trip details and ask the traveler to approve them.
  • Restrict document access to the traveler, use encryption and documented retention/deletion policies; avoid public exposure of PNR and personal details.
  • Never automatically query PNR, waitlist status or provider booking systems in the initial MVP.

M1–M6 Detailed Milestone Acceptance Criteria (v0.6)

Authority: Proposed acceptance specification for future implementation. PASS requires actual evidence from running tests; none is claimed in this research draft. Complete each milestone before beginning the next.

M1 — Project Foundation

  1. M1-01 Frontend: Next.js application starts and renders its home page.
  2. M1-02 Backend: FastAPI starts and responds successfully to a health endpoint.
  3. M1-03 Database: PostgreSQL connectivity and basic read/write tests pass.
  4. M1-04 Authentication: Sign-up, login and logout work securely.
  5. M1-05 Integration: Frontend successfully communicates with backend.
  6. M1-06 Security: Secrets remain server-side and protected endpoints reject unauthorized requests.
  7. M1-07 Configuration: Development and production settings are separated.
  8. M1-08 Testing: Automated foundation tests pass.
  9. M1-09 Documentation: Setup instructions and environment requirements are recorded.

M2 — Destination Discovery

  1. Search for a destination from a user-entered query rather than hardcoded Gujarat data.
  2. Display relevant nearby attractions, food and experiences, with provenance where available.
  3. Allow travelers to select and protect must-visit places.
  4. Handle no-result, partial-result and unavailable-data states clearly.

M3 — Transport Discovery

  1. Suggest discoverable train and bus route options, including multi-leg transfers where relevant.
  2. Label timetable details as indicative, show source and date/freshness caveats, and never imply live availability.
  3. Provide official provider search/verification links; do not imply a deep link selects the exact service unless verified.
  4. Allow users to select an option while it remains Not booked, or manually enter transport details.

M4 — Itinerary Planner

  1. Generate the full editable itinerary from selected attractions and transport before any booking.
  2. Account for journey dates, overnight arrivals, transfer buffers and realistic activity windows.
  3. Detect and explain infeasible connections and overloaded days.
  4. Preserve mandatory stops; propose alternatives or additional days rather than silently removing them.
  5. Recalculate affected legs and days when selections change.

M5 — Trip Management

  1. Save and retrieve trips and track indicative budget estimates separately from confirmed spending.
  2. Allow optional private upload of ticket or accommodation confirmations.
  3. Extract booking details and request user confirmation before updating the itinerary.
  4. Recheck timing conflicts after confirmed details change; provide private access and deletion controls.

M6 — Integrated Validation

  1. Run an end-to-end planning journey for Hyderabad → Manali, including selected train/bus options and nearby attractions.
  2. Run an end-to-end journey for Hyderabad → Mata no Madh, including multi-city connections and protected must-visit destinations.
  3. Confirm all applicable M1–M5 acceptance tests and end-to-end regression checks pass.
  4. Confirm both trips can be fully planned without a ticket purchase, booking API, live PNR or payment integration.

Release gate: No milestone is marked PASS without actual test evidence. M6 acceptance is not equivalent to production launch approval; data rights, privacy/security and operating-cost checks remain applicable.
